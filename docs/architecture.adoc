= hostlib: architecture
:toc:

== Abstract

hostlib is five packages under one name: `models` holds the dataclasses and nothing else; `proc` starts processes and builds their records; `sink` defines where output goes while a process runs and ships four destinations; `facts` says what the host is; `cli` is the `hostlib` command. Dependencies run one way, from behaviour to models to the standard library, and the public surface is what the top-level package re-exports. The load-bearing decisions are three: every process is read by two threads from the moment it starts; the record is built exactly once, from the exited process, by whichever caller asks first; and a foreground run is a background run that waits.

== Layout and the direction of dependency

The package is split by domain rather than by layer. `hostlib.models` contains `JobSpec`, `JobResult`, `JobStarted`, `JobLogs`, `HostFacts` and `ProgressEvent`, one module per domain, and imports only the standard library; it is the shape of everything that crosses a wire or lands in a file, and it has no behaviour beyond turning itself into plain data. `hostlib.proc`, `hostlib.sink` and `hostlib.facts` import `models` and may not import each other, with one exception: `proc` imports the sink protocol and the shipped sinks, because a process is started with a sink attached and a handle must be able to find the file sink's log paths. `hostlib.cli` imports anything; nothing imports it. The rule is enforced by convention and by the tests, which import each domain package in isolation.

This is the arrangement the mise framework arrived at for the same reason: when models live apart from behaviour, a client that only needs to read a record, a web console, a message consumer, a test, imports the shapes and nothing that spawns processes. Growth lands as a sibling package with its own module under `models`, not as a new file in a flat directory.

== Starting a process

`job_start` validates that the argument list is not empty, builds the environment by laying the spec's additions over the caller's, and calls `subprocess.Popen` with both output streams piped, standard input piped only when the spec provides text for it and otherwise connected to nothing, and `bufsize=0`. The last choice matters: an unbuffered pipe returns whatever bytes are available on each read instead of waiting to fill a buffer, which is what makes a progress line written with a carriage return and no newline reach a sink while the program is still drawing it. The process is wrapped in a `JobHandle`, whose constructor records the host's facts and the start time, tells the sink the job has begun, starts one `StreamReader` thread per pipe, and feeds and closes standard input.

A `StreamReader` reads up to 64 KiB at a time, passes the bytes through an incremental decoder with replacement for undecodable input, appends the text to its own list, and hands the same text to its callback, which is the sink's `stdout_write` or `stderr_write`. The incremental decoder is why a multi-byte character split across two reads is still one character; the per-pipe thread is why neither stream can block the other; reading to end of file rather than polling the process is why the last line is kept whether or not it ended in a newline. The readers are daemon threads, so a caller that abandons a handle does not keep the interpreter alive.

The exceptions `Popen` raises when a program cannot be started, not found, not executable, a working directory that does not exist, are allowed to propagate from `job_start`: a caller who asked for a handle to a background job needs to know there is none. `job_run` catches them and returns a failed record with no exit status, no pid, and the operating system's reason in words, because a caller who asked for a result wants one whatever happened.

== The record, once

`JobHandle.result` returns `None` while the process runs. Once it has exited, the method takes a lock, joins both readers so that every byte the process wrote has been read and decoded, assembles the `JobResult`, tells the sink the job has ended, stores the record, and returns it; a second call returns the stored record without rebuilding it or notifying the sink again. `wait` is `Popen.wait` with an optional timeout followed by `result`, returning `None` if the timeout elapsed, and terminating nothing. `terminate` marks the handle as timed out, sends SIGTERM, waits a grace period, sends SIGKILL if needed, and returns the record, whose `timedOut` is set and whose `status` is false regardless of the exit status the signal produced.

The record's `status` is the conjunction of a zero exit status and not having been terminated, computed from the process and never from its output. Its `errors` carry one sentence for a non-zero exit and one for a timeout, so the record explains itself. `toRecord` on a running handle produces a `JobStarted`, pid, argument list, working directory, start time, host facts and, if a file sink is attached directly or inside a tee, the four log paths: what a service that started a job tells a client that asks about it.

`job_run` is `job_start` followed by `wait` with the spec's timeout, and `terminate` if the wait returns `None`. One implementation serves both the foreground and the background; the foreground is the special case.

== Sinks

`JobSink` is a `typing.Protocol` with six methods: `began` with the argument list, `stdout_write` and `stderr_write` with a decoded chunk each, `status_write` with an ephemeral line, `progress_write` with a `ProgressEvent`, and `ended` with the record. The four channels mirror the output sink the mise framework gives a surface, data, error, status and progress, and the two bookends are what a file sink needs to write the command before anything runs and the exit status after everything has. `SinkBase` implements all six as no-ops so that a custom sink overrides only what it cares about; `NullSink` is `SinkBase` under a name that says what it does.

`ConsoleSink` writes stdout chunks to one text stream and stderr chunks, status lines and progress events to another, flushing after each, so a terminal shows output in the order it arrived and keeps the two streams apart. `FileSink` takes a path prefix; on `began` it creates the parent directory, writes `<prefix>-cmd` as a shell-quoted command line, and opens `<prefix>-stdout` and `<prefix>-stderr`; each chunk is written and flushed, so a job that is killed still leaves what it printed; on `ended` it closes both and writes `<prefix>-returncode`. `TeeSink` forwards every call to each sink it holds, in order. A sink runs on the reader threads, so a slow sink slows the pipe it serves and no other; a sink that raises is a bug in the sink and will surface as one.

== Facts

`facts()` returns a `HostFacts`: hostname, user, pid, platform string, working directory and an ISO 8601 timestamp with the local offset. It is called once per handle at start and stored in the record. Looking the user up can fail in a container with no passwd entry; the function returns an empty string rather than raising, because a missing user name should not prevent a job from running.

== Commands as text

`argv_fromTemplate` is `shlex.split` in POSIX mode, wrapped so that an unclosed quote raises a `ValueError` that names the command. `argv_join` is `shlex.join`. The library deliberately offers nothing between them: substitution of values into the split arguments is the caller's concern, done with whatever templating it already has, and keeping it outside hostlib keeps hostlib free of opinions about tag syntax. What hostlib guarantees is the order, split first, substitute second, which is what makes a substituted value unable to change the shape of the command.

== The command

`hostlib run` parses its own options, treats everything after `--` as the program and its arguments, builds a `ConsoleSink` unless `--quiet`, a `FileSink` if `--log`, a tee of both if both, runs the job and exits with the program's exit status, 127 if it could not be started and 124 if it timed out, the conventions of the shell and of `timeout`. With `--json` it prints the record. `hostlib facts` prints the host's facts. `--man` and `--synopsis` render a manual page through `hostlib.cli.manual`, a copy of pftree's renderer kept in hostlib so that the library has no dependency on the pf* stack it serves: a banner, the page set on a black background padded to the terminal width, headings in yellow, command lines highlighted token by token, inline code in prose coloured on a terminal and stripped of its backticks in a pipe.

== Verification

The tests run real processes, Python itself invoked with `-c`, so that they are portable and the program's behaviour is exact. They cover success with both streams, a non-zero exit, a program that does not exist, an empty argument list, an argument containing a space and a semicolon that arrives as one argument, a last line without a newline, two megabytes on each stream read without deadlock, a multi-byte character split across reads, standard input fed and closed, working directory and environment applied, a working directory that does not exist, a timeout that terminates, output reaching a sink before the process exits, a carriage-return progress line, the console and file sinks together; and for background jobs, a handle returned at once, polling, a wait that times out without terminating, the record built once and the sink told once, termination by SIGTERM and by SIGKILL after a program that ignores SIGTERM, the file sink writing while the job runs, and the started record naming its logs. The command is tested through `main`: exit status pass-through, JSON output, the 127 and 124 conventions, logs, environment, working directory, standard input, usage errors, facts, version, and the manual's headings, colours and padding. Continuous integration runs the suite on Python 3.11 through 3.14 and the free-threaded 3.14t, and publishes to PyPI from a version tag through trusted publishing.
