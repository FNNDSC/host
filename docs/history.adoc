:toc:

== Abstract

hostlib was created in October 2026 as the single home for a piece of code that had been copied, by hand, into at least sixteen FNNDSC repositories over six years: a class, usually called `Jobber` or `jobber`, that ran a shell command from Python and returned a dictionary of what happened. Every copy carried the same defects. hostlib replaces them with one implementation, shaped by what the mise framework had learned about carrying a command's outcome as a typed envelope rather than as printed text.

== 2020 to 2023: the jobber lineage

The pattern began in pfdo_run in August 2020, where a `job_run` method took a command as a string, split it on whitespace, started it with `subprocess.Popen`, read standard output a line at a time so that the user could watch, and read standard error only after the process had exited. It returned a dictionary with `stdout`, `stderr`, `cmd`, `cwd` and `returncode`, and a companion `job_stdwrite` wrote each key to a file beside the job's results. It worked well enough for the short, quiet commands it was first used on.

In 2021 and 2022 the method was lifted, with its dictionary, into a `Jobber` class and copied into whatever needed to run a command: the ChRIS plugins pl-dylld, pl-dyworkflow, pl-dypi and pl-diff_unpack, the service plugin2cube, the mail tool mbox2m365, the storage layer cfs, and, as a `jobController` module, the FastAPI services pfdcm, pfchrs, pfmdb, pftel, pfbridge, pfair and pf_build. Two of the service copies grew a `job_runbg` method for background work, which wrote the command into a dated shell script with an ampersand appended, started the script, and returned the user id, the working directory and the script's path, never waiting and never reading the pipes it had opened. The copies drifted in whitespace and in small additions, `dict2cli` to turn a dictionary into flags, a `/tmp/job.json` written on every run, an `XDG_CONFIG_HOME` set at import, and otherwise stayed identical, down to the same comment explaining that running a process from Python is cumbersome.

Each copy had the same four faults, none of which showed in a short test. Splitting on whitespace broke on any path with a space; the plugins worked around it by writing the command into a script and running the script. Reading standard error after exit deadlocked on any program that wrote more than a pipe's worth of it. Checking for exit between reads dropped the last line of output. Decoding line by line split multi-byte characters. The dictionary result pushed callers into parsing standard output for the facts they needed; one plugin found a plugin-instance id by splitting stdout and taking the third word. None of this was fixed anywhere because there was nowhere to fix it: the code lived in sixteen places and in none of them was it the point.

== 2026: the pf* revitalization and the envelope

In October 2026 the pf* stack, pftree, pfdo, pftag and pfdo_run, was rebuilt in turn, each as a modern package with tests, continuous integration and trusted publishing. pfdo_run 4.0 rewrote `job_run` correctly for the first time: the command split once with `shlex`, tags substituted per argument, the process run without a shell, both streams captured by `subprocess.run`. It fixed the splitting, the deadlock, the dropped line and the decoding, and in doing so dropped the one thing the old code had tried to offer, output visible while a long job ran. The rewrite was also bound to pfdo_run's own types, a directory node and a tag engine, so pfdcm and pl-dylld could not import it.

The comparison between that rewrite and pl-dylld's `jobber.py` made the case for a separate library, and the mise framework supplied its shape. mise's engine returns every command's outcome as a `CommandEnvelope`, a status that is the engine's ground truth, rendered text that is only a view, a typed model that is the source of truth, and structured errors; its surfaces receive output while a command runs through an `OutputSink` with data, error, status and progress channels; a scheduled run is reported to a client as a small typed record of what was started and where to find it. Each of these had a direct counterpart in what the jobber copies had been reaching for and missing: a `JobResult` whose status is never inferred from its text; a `JobSink` fed while the process runs; a `JobStarted` for a service to hand back.

The library was named `host`, for the thing a process stands on, and renamed `hostlib` within the hour when PyPI reported `host` as a prohibited name; the longer name was kept for the package and the repository too, on the grounds that `host` alone was too generic to import. Version 1.0.0 shipped the five packages, `models`, `proc`, `sink`, `facts` and `cli`, with no dependencies, sixty-one tests run on five interpreters, and the manual page the pf* commands print. It was built as the engine for pfdo_run 4.1 and, through it, pl-shexec and pl-freesurfer, and to replace the service copies as each service is next rebuilt.

Version 1.2.0 added `JsonSink`, one line of JSON per ended job appended to a file, and `hostlib run --jsonl`. It came from asking, once pflog 2 wrote a span as a JSON line and `pflog read` printed job lines beside them, why pfdo_run still wrote each job as four files; the four files carry a projection of the record in a form only `cat` reads, and the JSON line carries the whole of it in the form a reader and a collector parse. pfdo_run 4.2 made the JSON line its default and the four files an option.

Version 1.3.0 added `memory_limit` and `memorySize_parse`. The occasion was pl-freesurfer: outside ChRIS, on a workstation, a Slurm node or under Apptainer, running several `recon-all` at once is reasonable as long as each has its roughly sixteen gigabytes, and the plugin needs to know how much memory is actually its own. The fact belongs with the host's other facts, so it is here rather than in shexec, which uses it to cap `--threads`. It was checked on pangea in three places: a container started with `--memory=3g` read 3 GiB from its cgroup, an uncapped container read the machine's available memory, and a systemd scope with `MemoryMax=5G`, the mechanism Slurm uses for `--mem`, read 5 GiB.
